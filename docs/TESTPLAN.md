# Student Account Application Test Plan

This test plan documents the current behavior of the COBOL account-management application. It is intended for review with business stakeholders before the application is transformed into Node.js. `Actual Result` and `Status` are intentionally left blank for test execution.

## Test Cases

| Test Case ID | Test Case Description | Pre-conditions | Test Steps | Expected Result | Actual Result | Status (Pass/Fail) | Comments |
|---|---|---|---|---|---|---|---|
| TC-001 | Start a new account with the default balance | Start a fresh application process. | 1. Launch `MainProgram`.<br>2. Select `1` (View Balance). | The application displays a current balance of `1000.00`. |  |  | Confirms the initial value in `DataProgram`. |
| TC-002 | Display the account menu | Application is running. | 1. Observe the menu displayed by the application. | The menu displays View Balance, Credit Account, Debit Account, and Exit options numbered 1 through 4. |  |  |  |
| TC-003 | View the current balance after startup | Application is running with the default balance. | 1. Select `1`.<br>2. Observe the response. | `Operations` reads the stored balance and displays `Current balance: 1000.00`. |  |  | Covers the `TOTAL ` operation. |
| TC-004 | Credit the account with a positive amount | Fresh application process with balance `1000.00`. | 1. Select `2`.<br>2. Enter `250.50`.<br>3. | TC-005 | Credit the account with a whole-number amount | Fresh application process with balance `1000.00`. | 1. Select `2`.<br>2. Enter `100`.<br>3. | TC-006 | Credit the account with zero | Fresh application process with balance `1000.00`. | 1. Select `2`.<br>2. Enter `0`.<br>3. | TC-007 | Credit the account with a negative amount | Fresh application process with balance `1000.00`. | 1. Select `2`.<br>2. | TC-008 | Debit the account with a valid amount | Fresh application process with balance `1000.00`. | 1. Select `3`.<br>2. Enter `250.50`.<br>3. Select `1`. | The debit is accepted, the application displays a new balance of `749.50`, and a subsequent balance inquiry returns `749.50`. |  |  | Covers read, sufficient-funds check, subtract, write, and display behavior. |
| TC-009 | Debit the exact available balance | Fresh application process with balance `1000.00`. | 1. Select `3`.<br>2. Enter `1000.00`.<br>3. Select `1`. | The debit is accepted because the check is `balance >= amount`; the new balance is `0.00`. |  |  | Confirms the boundary condition for sufficient funds. |
| TC-010 | Reject a debit greater than the available balance | Fresh application process with balance `1000.00`. | 1. Select `3`.<br>2. Enter `1000.01`.<br>3. Select `1`. | The application displays `Insufficient funds for this debit.`; no write occurs and the balance remains `1000.00`. |  |  | Confirms overdrafts are rejected. |
| TC-011 | Reject a debit after prior transactions when funds are insufficient | Fresh application process. | 1. Credit `200.00`.<br>2. Debit `1200.01`.<br>3. Select `1`. | The balance before the debit is `1200.00`; the debit is rejected and the final balance remains `1200.00`. |  |  | Confirms the check uses the latest stored balance. |
| TC-012 | Debit the account with zero | Fresh application process with balance `1000.00`. | 1. Select `3`.<br>2. Enter `0`.<br>3. Select `1`. | Current implementation accepts the amount, writes the unchanged balance, and displays `1000.00`. |  |  | Stakeholders should confirm whether zero-value debits should be accepted. |
| TC-013 | Debit the account with a negative amount | Fresh application process with balance `1000.00`. | 1. Select `3`.<br>2. Enter a negative amount supported by the runtime, such as `-50.00`.<br>3. Select `1`. | The current implementation has no positive-amount validation. Verify the compiler/runtime behavior; if accepted, subtracting a negative amount increases the balance to `1050.00`. |  |  | This is a current behavior and validation gap for the Node.js migration. |
| TC-014 | Preserve a successful transaction across menu operations | Application is running. | 1. Credit `100.00`.<br>2. View the balance.<br>3. Debit `25.00`.<br>4. View the balance again. | The first balance inquiry returns `1100.00`; the final balance inquiry returns `1075.00`. |  |  | Confirms `DataProgram` storage is shared across calls during one process. |
| TC-015 | Keep the balance unchanged after a rejected debit | Fresh application process with balance `1000.00`. | 1. Attempt to debit `1000.01`.<br>2. View the balance. | The insufficient-funds message is displayed and the balance remains `1000.00`. |  |  | Confirms the rejected branch does not call `WRITE`. |
| TC-016 | Reject an invalid menu choice | Application is running. | 1. Enter `5` at the menu.<br>2. Observe the response.<br>3. Enter `1` to view the balance. | The application displays `Invalid choice, please select 1-4.` and continues running. The subsequent valid choice displays the current balance. |  |  | Covers the `WHEN OTHER` branch and loop continuation. |
| TC-017 | Exit the application | Application is running. | 1. Select `4`.<br>2. Observe the response. | The application sets the continue flag to `NO`, leaves the menu loop, displays `Exiting the program. Goodbye!`, and stops. |  |  | Covers normal termination. |
| TC-018 | Enter malformed numeric input for a transaction amount | Application is running and a credit or debit operation is selected. | 1. Select `2` or `3`.<br>2. Enter nonnumeric input, such as `ABC`.<br>3. Observe the result and subsequent menu behavior. | The current source does not define explicit input validation or an error message. Record the actual compiler/runtime behavior and agree the required Node.js behavior with stakeholders. |  |  | Migration decision point; do not infer a desired rule from the COBOL source. |
| TC-019 | Read a stored balance through the data program | `DataProgram` is available to be called. | 1. Call `DataProgram` with operation `READ` and a balance field.<br>2. Inspect the returned field. | The passed balance field receives the current stored balance. |  |  | Unit-level test for the `READ` operation. |
| TC-020 | Write and then read a stored balance through the data program | `DataProgram` is available to be called. | 1. Set a balance field to `1234.56`.<br>2. Call `DataProgram` with operation `WRITE`.<br>3. Call it again with `READ`.<br>4. Inspect the returned field. | The subsequent read returns `1234.56`. |  |  | Unit-level test for `WRITE` persistence during one process. |
| TC-021 | Ignore an unsupported data operation | `DataProgram` is available to be called. | 1. Set a balance field to a known value.<br>2. Call `DataProgram` with an operation other than `READ` or `WRITE`.<br>3. Inspect the stored and passed values. | The current implementation performs no action and returns without an error. | TC-022 | Handle an unsupported operations command | `Operations` is available to be called. | 1. Call `Operations` with an operation other than `TOTAL `, `CREDIT`, or `DEBIT `.<br>2. Observe the result. | The current implementation performs no action and returns without an error or transaction message. Record whether explicit command validation is required in Node.js. |  |  | Covers the implicit no-op path in `Operations`. |
| TC-023 | Verify the supported amount range and precision | Application is running. | 1. Credit or debit values with two decimal places.<br>2. Repeat with a value containing more than two decimal places.<br>3. Repeat with a value exceeding six whole-number digits, subject to runtime input limits. | Values are constrained by `PIC 9(6)V99`: up to six whole-number digits and two implied decimal places. Record rounding, truncation, rejection, or runtime behavior for out-of-range input. |  |  | Stakeholders should define the Node.js equivalent precision and range rules. |
| TC-024 | Verify a new process resets the in-memory balance | Complete a transaction in one application process, then terminate it and start a fresh process. | 1. In the first process, credit `100.00`.<br>2. Exit.<br>3. Start a new process.<br>4. View the balance. | The new process starts at `1000.00`; the prior process balance is not persisted. |  |  | Confirms there is no file or database persistence. |

## Execution Notes

- Execute cases against the current COBOL application before using the results as migration acceptance criteria.
- For each case, record the observed behavior in `Actual Result`, mark `Status (Pass/Fail)`, and use `Comments` for discrepancies or stakeholder decisions.
- Cases TC-006, TC-007, TC-012, TC-013, TC-018, TC-021, TC-022, and TC-023 intentionally expose behavior that is not fully specified as a business rule. These cases require stakeholder decisions before the Node.js implementation is finalized.
